## Q. vault에서 key는 암호화 안되고, value만 암호화 되는거 맞지? (2026-08-26)

**A.**
맞다. `hashicorp/vault` 소스(`vault/barrier_aes_gcm.go`) 기준, Barrier의 Put 로직은 `b.encryptTracked(entry.Key, term, primary, entry.Value)`로 **entry.Value만 암호화**하고, 저장되는 `physical.Entry`는 `Key: entry.Key`(평문) / `Value: value`(암호문)로 구성된다.

- **왜 경로(Key)는 평문으로 두나**: 경로까지 암호화하면 Storage Backend가 prefix 기반 `List`(경로 나열) 연산을 할 수 없기 때문. 저장 경로는 평문으로 남겨 Storage가 정상적으로 키를 다루게 하고, 실제 민감한 내용(Value)만 암호화한다.
- **"key"의 두 가지 의미를 구분해야 함**:
  1. 저장 경로(storage path, 예: `secret/myapp`) — 암호화 안 됨(평문).
  2. KV 시크릿 안의 필드 이름(예: `password=1234`의 `password`) — `{"password":"1234"}` 전체가 JSON 직렬화된 뒤 Value로서 통째로 암호화되므로, 필드명도 결과적으로 암호화된 블록 안에 들어가 보호됨.
- 이 동작은 KV 시크릿 엔진만의 특징이 아니라, Barrier를 거치는 **모든 Secrets Engine의 저장 데이터에 공통 적용**되는 구조다.

## Q. 아키텍처에서 https의 경우 처음 만들면 인증 없는데 어떤 인증서 사용하는거임? (2026-08-27)

**A.**
TLS 인증서는 Vault의 로그인/인증(auth method) 시스템과는 완전히 별개인 **전송 계층(TLS handshake)** 문제다. init/unseal(=Vault 애플리케이션 레벨 인증이 아직 없는 상태)이 되기 전이라도 HTTPS 자체는 이미 성립돼 있어야 `/v1/sys/init` 같은 API를 호출할 수 있으므로, TLS 준비는 init보다도 먼저 끝나 있어야 하는 전제조건이다.

- **프로덕션**: Vault는 인증서를 자동 생성하지 않는다. `listener/tcp` 문서 기준 `tls_cert_file`/`tls_key_file`은 `(string: <required-if-enabled>)`이며, Vault는 기본적으로 TLS를 가정하므로("Vault assumes TLS by default") 운영자가 미리 발급받은 인증서(사내/외부 CA 서명 또는 self-signed)를 서버 시작 전에 배치해두거나 `tls_disable = true`로 명시적으로 꺼야 한다.
- **`vault server -dev`**: TLS 없이 순수 HTTP로 in-memory 서버가 뜨고 이미 unsealed 상태로 시작한다(인증서 자체가 필요 없음). "처음 만들었는데 인증 없이 됐다"는 경험은 대개 이 모드였을 가능성이 크다.
- **`vault server -dev-tls`**: 이 경우에만 Vault가 자체적으로 self-signed CA + cert + key를 생성해 `-dev-tls-cert-dir`(미지정 시 임시 디렉터리)에 저장한다. 이 역시 in-memory + 이미 unsealed로 시작하는 개발 전용 모드다.

## Q. 용어/아키텍쳐에도 proxy, agent 추가(enterprise) 의 기능을 추가해서. (2026-08-27)

**A.**
Agent와 Proxy는 Vault 서버 프로세스의 일부가 아니라 애플리케이션 옆(사이드카/로컬 프로세스)에서 도는 클라이언트 데몬이라, `01_아키텍쳐.md`에서 이미 설명한 Listener → Core → Router → Backend → Barrier → Storage 흐름 **바깥**에 위치한다. Vault 서버 입장에서는 Agent/Proxy도 Auth Method로 인증하는 여느 클라이언트와 다를 바 없다.

- 애플리케이션은 Agent/Proxy가 로컬에 여는 API Proxy(주로 Proxy 담당) 또는 Agent가 렌더링한 시크릿 파일(Templating)을 통해 시크릿에 접근하고, 실제 Vault 인증(Auto-Auth)·캐싱은 데몬이 대신 처리한다.
- 두 데몬 모두 OSS 바이너리에 기본 포함이라 "전체가 Enterprise 전용"은 아니다. 다만 Proxy의 정적 시크릿(KV) 캐싱은 캐시 무효화에 KV Event Notifications 구독이 필요하고, Event Notifications 자체가 "Appropriate Vault Enterprise license required"로 명시된 Enterprise 전용 기능이라 이 기능만 사실상 Enterprise 전제다.
- Agent의 API Proxy 기능은 지원 중단(Deprecated)되어 공식문서가 Proxy 사용을 권장하지만, Templating/Process Supervisor는 Proxy에 없으므로 Agent가 완전히 대체된 것은 아니다.

## Q. 시크릿엔진은 어떻게 분기되는거임? database는 저장한다고 치고, aws/gcp 같은 클라우드는 엔드포인트가 다른지? (2026-08-26)

**A.**
맞다. AWS와 GCP는 서로 다른 클라우드 API를 호출하고, Database도 내부적으로는 DB 종류별로 다른 프로토콜을 쓴다. 이는 Vault의 **Plugin 구조** 때문이다.

- KV/PKI/Transit/Database/AWS/GCP는 모두 "Secrets Engine"으로 묶이지만 실제로는 각각 독립된 **Plugin**이며, Vault Core와는 mTLS 기반 RPC(gRPC)로 통신한다. Built-in Plugin(KV/PKI/Transit)은 Vault 바이너리에 포함되어 프로세스 내에서 실행되고, External Plugin(Database 하위 드라이버, 클라우드 벤더 플러그인 등)은 별도 프로세스로 실행된다.
- Vault Core/Router는 "발급해라/회수해라"라는 **공통 인터페이스**만 알고, 실제로 어떤 외부 시스템과 어떻게 통신할지는 각 플러그인 구현이 결정한다.
- **Database**: "저장"이 아니라 `plugin_name`으로 지정한 DB별 하위 플러그인(`postgresql-database-plugin` 등)이 그 DB의 고유 SQL wire protocol로 `CREATE USER`/`DROP USER`를 실제 DB에 실행하는 것.
- **AWS**: `credential_type`별로 다른 API — `iam_user`→`iam:CreateUser`/`iam:CreateAccessKey`, `assumed_role`→`sts:AssumeRole`, `federation_token`→`sts:GetFederationToken`, `session_token`→`sts:GetSessionToken`.
- **GCP**: roleset 방식이면 `iam.serviceAccounts.create` 등 GCP IAM API, impersonated 방식이면 `iam.serviceAccounts.getAccessToken`.
- **PKI/Transit**은 외부 API를 아예 호출하지 않는다 — Vault 내부에서 서명/암호화 연산만 수행한다.

즉 "엔드포인트가 다른가?"의 답은 **그렇다** — Postgres는 SQL wire protocol, AWS는 IAM/STS REST API, GCP는 GCP IAM API로 완전히 다른 통신을 한다.

## Q. aws credential을 생성한다면, aws iam의 인증 토큰을 vault에 보관 후, vault에서 ttl이 있는 토큰을 등록된 api를 사용해 발급해와서 사용자에게 accesstoken을 주는구조지? 발급/관리를 대행한다는게 핵심이지? (2026-08-26)

**A.**
"발급/관리를 대행한다"는 큰 틀은 맞다. Vault는 `aws/config/root`에 관리자급 IAM access key/secret key(root credential)를 저장해두고, 사용자는 이 credential을 직접 만지지 않는다. 사용자가 `aws/creds/<role>`을 요청하면 Vault가 root credential로 AWS API를 대신 호출해 새 자격증명을 만들어 반환한다.

다만 **"TTL이 있는 토큰을 발급해온다"는 그림은 `credential_type`에 따라 정확도가 다르다**:

- **`assumed_role` / `federation_token` / `session_token`(STS 기반)**: 질문하신 그림 그대로다. Vault가 `sts:AssumeRole` 등 STS API를 호출하면, AWS가 **자체적으로 TTL을 내장한** 임시 자격증명(access_key+secret_key+session_token)을 돌려준다. 만료도 AWS가 자동으로 처리하므로 Vault가 따로 지울 게 없다.
- **`iam_user`**: 반대 구조다. Vault는 IAM API(`iam:CreateUser`, `iam:CreateAccessKey`)로 **새 IAM 사용자와 영구 액세스 키**를 그 자리에서 생성한다 — 이 키 자체는 AWS 입장에서 만료 개념이 없다. TTL은 **Vault의 Lease가 자체적으로 추적**하다가, 만료 시점에 Vault가 능동적으로 `iam:DeleteAccessKey`/`iam:DeleteUser`를 호출해 **직접 삭제(회수)**한다. "발급해온다"보다는 "새로 만들고 나중에 직접 지운다"에 가깝다.

즉 공통 핵심은 **root credential을 Vault가 대신 보관하고 사용자와 격리시킨다**는 점이지만, TTL을 누가 관리하는지(AWS 자체 vs Vault의 Lease)는 credential_type마다 다르다.

**관련 노트:** [`notes/03_시크릿엔진.md`](../notes/03_시크릿엔진.md#aws--root-credential을-이용한-발급-대행-구조)

## Q. transit의 동작과 사용방법에 대한 상세한 설명. 일치하지않으면 fast-fail의 false 반환인지에 대한 여부. (2026-08-26)

**A.**
Transit은 "Cryptography as a Service" 엔진으로, "Vault doesn't store the data sent to the secrets engine"(공식문서) — 데이터를 저장하지 않고 암호화 연산만 대행한다. 지원 키 타입은 대칭(`aes256-gcm96` 등)/비대칭 서명(`ed25519`, `rsa-*` 등)/HMAC 세 갈래이며, 주요 연산은 Encrypt/Decrypt, Sign/Verify, HMAC/Verify, Datakey(봉투 암호화), Rewrap(재암호화), Key Derivation, Convergent Encryption, Rotate다.

**HMAC/Verify API:**
- `POST /transit/hmac/:name` — `input`(base64), `algorithm`(기본 sha2-256) → `{ "hmac": "vault:v1:..." }`
- `POST /transit/verify/:name` — `input` + `hmac`(또는 `signature`) → `{ "valid": true/false }`

**질문 핵심(불일치 시 fast-fail false 반환 여부):**
**맞다, 단 "정상 응답 안에서" false를 반환하는 것이지 요청 자체가 실패(에러)하는 게 아니다.** 두 가지 독립된 소스로 교차 확인했다.
1. HashiCorp 공식 예제 리포지토리(`hashicorp/vault-guides`, `encryption/transit-signing/README.md`)의 실제 CLI 출력: 수정된 데이터나 다른 서명으로 검증해도 `Key Value / valid false`로 **정상 200 응답**이 온다. 에러가 발생하는 건 서명 값 자체가 손상돼 base64 디코딩이 실패하는 경우뿐이며, 이때만 `Code: 400, invalid base64 signature value`가 뜬다.
2. Vault 소스코드(`hashicorp/vault`, `builtin/logical/transit/path_sign_verify.go`의 `pathVerifyWrite` 핸들러): `VerifySignatureWithOptions`가 에러를 반환하지 않는 한 `response[i].Valid = valid`로 정상 응답에 결과를 담아 리턴한다. 에러 응답(4xx)은 검증 함수 자체가 에러를 던질 때(입력 형식 문제)만 발생한다.

즉 "값이 다름"(200 + valid:false)과 "입력 형식이 잘못됨"(400 에러)은 서로 다른 실패 경로이므로, 호출 측에서 이 둘을 구분해 처리해야 한다 — 예를 들어 API 게이트웨이가 이 결과로 인증 여부를 판단하는 시나리오라면 `valid:false`는 401(인증 실패)로, HTTP 요청 자체의 실패는 별도 오류로 매핑하는 것이 자연스럽다.

Encrypt/Decrypt, Key Rotation(`min_decryption_version`/`min_encryption_version`) 등 나머지 상세는 노트 참고.

## Q. transit은 hmac으로 생성했을때, 처리후 결과인 해시값을 반환해줄뿐이지? 또한 내가 검증을 받기위해 verify요청을 보내면 그것을 다시 서버만 알고있는 비밀키로 처리해서, 그 결과인것이 존재하는지를 보여주는거지? 내가 설명하는 로직이 맞니. (2026-08-26)

**A.**
정확하다. Vault 소스코드(`hashicorp/vault`, `builtin/logical/transit/path_hmac.go`)로 직접 확인했다.

**생성(HMAC)**: `key, err := p.HMACKey(ver)`로 Transit 키링 안에만 존재하는 비밀 키를 꺼내 `hmac.New(hashAlg, key)` → `hf.Write(input)` → `hf.Sum(nil)`로 해시를 계산한다. 이 비밀 키 자체는 API 응답에 절대 포함되지 않고, **계산된 해시값(`retBytes`)만** base64로 인코딩돼 응답으로 나간다. 질문하신 "처리 후 결과인 해시값을 반환해줄 뿐"이 정확하다.

**검증(Verify)**: 클라이언트가 제출한 "현재 input"을 서버가 **같은 비밀 키로 다시 HMAC을 계산**한다(`key, err := p.HMACKey(ver)` 재사용 → 동일한 로직으로 재계산). 그 재계산 결과를 클라이언트가 함께 제출한 hmac 값(`verBytes`)과 `hmac.Equal(retBytes, verBytes)`로 비교해 boolean을 반환한다. "저장된 값을 그대로 조회해서 비교"하는 게 아니라 **매 요청마다 서버가 재계산해서 비교**하는 구조이며, 이 비교 결과가 곧 "일치하는지"에 대한 답이다 — "존재하는지"보다는 "일치하는지"라는 표현이 더 정확하지만, 로직 자체는 질문하신 그대로다.

**보너스로 확인된 사실**: 이 비교에 일반 `==`가 아니라 `hmac.Equal`(Go `crypto/hmac`의 상수시간 비교 함수)을 쓴다. 애플리케이션이 직접 문자열 비교로 구현하면 언어/런타임에 따라 상수시간이 보장되지 않을 수 있는데, Transit `verify`를 채택하면 이 문제가 Vault 내부에서 이미 안전하게 해결된다.

**관련 노트:** [`notes/03_시크릿엔진.md`](../notes/03_시크릿엔진.md#내부-동작-비밀-키는-절대-밖으로-안-나가고-검증은-재계산-후-비교)

## Q. verify도 write 부분이 똑같이 있는데, verify는 저장이 되면 안될것같은데 이 부분이 왜 있는지. (2026-08-26)

**A.**
직감이 맞다 — **verify는 실제로 아무것도 저장하지 않는다.** 다만 CLI 명령이 `vault write`인 이유는 "저장 여부"가 아니라 **"HTTP 메서드가 POST인가 GET인가"**에 대응하기 때문이다.

공식문서(`/vault/docs/commands/write`): "The `write` command writes data to Vault at the given path (wrapper command for HTTP PUT or POST)... **The specific behavior of the write command is determined at the thing mounted at the path.**" — 즉 `write`/`read`는 각각 POST/GET에 대응하는 **범용 CLI 래퍼**일 뿐이고, 그 경로에서 실제로 무슨 일이 일어나는지는 **마운트된 플러그인이 결정**한다. KV라면 write가 실제 storage에 값을 쓰지만, Transit의 `verify`/`hmac`/`sign`은 (지난 질문에서 소스코드로 확인했듯 `path_hmac.go`, `path_sign_verify.go`에 storage 쓰기 호출이 없다) 저장 없이 계산만 하고 결과를 반환한다.

`write`(POST)를 써야 하는 실질적 이유는 **구조화된 파라미터를 요청 본문(body)으로 보내야 하기 때문**이다 — `input`, `hmac`/`signature`, `hash_algorithm`, `batch_input`(배열) 같은 값들은 GET의 단순 경로/쿼리스트링 조회 방식으로 보내기 적합하지 않다. 이 마지막 부분(GET이 body를 못 보낸다는 것)은 공식문서에 직접적인 문장으로 명시돼 있지는 않아 일반적인 HTTP 관례에 근거한 추론임을 밝힌다.

추가로 공식문서는 POST/PUT을 저장 여부와 무관하게 범용으로 쓴다는 것도 확인해준다: "Vault engines can implement an existence check to discover whether an operation is actually a create or update operation based on the data already stored within Vault" — POST가 create인지 update인지조차 Vault가 기존 데이터 존재 여부로 판단하지, 메서드 이름만으로 정해지지 않는다.

**정리**: "verify가 저장하면 안 될 것 같다"는 직감 → 맞다, 저장 안 한다. "근데 왜 write냐" → write는 저장을 뜻하는 이름이 아니라 "body 있는 POST 요청"을 뜻하는 이름이라서다.

## Q. 검증을 위해서는 verify에 파라미터로 암호화된 값/원본 값을 다 준 다음에 일치여부를 판단하는거지? POST는 vault의 secret엔진에 저장하는 개념이 아닌, 연산 값만 리턴하는 구조라는거지? (2026-08-26)

**A.**
첫 번째 질문(파라미터 구성)은 맞다 — `verify` 요청에는 **원본 후보값(`input`)**과 **기존에 발급받아 보관 중인 값(`hmac`/`signature`)**을 함께 보내고, Vault가 내부 비밀 키로 `input`을 재계산해 제출된 값과 일치하는지 비교해 boolean만 돌려준다.

다만 표현을 하나 정정하고 싶다: HMAC으로 얻은 값은 "**암호화된 값**"이 아니다. Encrypt/Decrypt는 양방향(디코딩 가능)이지만, HMAC은 **단방향(one-way)**이라 원본으로 되돌릴 수 없는 "다이제스트/지문"에 가깝다 — 비밀번호 해시(bcrypt 등)와 같은 성격이다. "암호화 vs 해시"를 구분해두는 게 이후 설계(유출 시 영향 범위 판단 등)에서 중요하다.

두 번째 질문(POST=저장 안 함)은 **일반화하면 틀렸다.** 지난 질문에서 확인했듯 `vault write`(POST)는 "저장"을 뜻하는 이름이 아니라 그냥 HTTP POST에 대응하는 범용 CLI 래퍼이고, **그 경로에 무슨 일이 일어나는지는 마운트된 엔진이 결정**한다. KV 엔진의 `write`는 실제로 storage에 저장하고, Transit의 `verify`/`hmac`/`sign`/`encrypt`/`decrypt`만 저장 없이 계산 결과를 리턴하는 것이다. 즉 "POST는 원래 저장 안 함"이 아니라 "Transit이라는 이 특정 엔진의 이 특정 연산들이 저장을 안 하는 것"이라고 정정한다.

## Q. 시크릿엔진의 transit의 경우, aes암호 방식을 채택하면 aes에 사용되는 key는 vault내부에 자동생성되고 비밀이 보장됨을 어떻게 보장하는지? (2026-08-27)

**A.**
"자동 생성"과 "비밀 보장"은 서로 다른 두 메커니즘이 함께 작동한 결과다.

**자동 생성**: Vault 소스코드(`sdk/helper/keysutil/policy.go`)의 키 생성/회전 로직이 `uuid.GenerateRandomBytesWithReader(numBytes, randReader)`로 필요한 바이트 수만큼 난수를 만들어 그대로 키로 쓴다. 이 헬퍼는 별도 리더를 넘기지 않는 한 Go 표준 `crypto/rand`(OS 엔트로피 기반 CSPRNG)를 사용하므로, 애플리케이션이 키를 만들어 넘기는 게 아니라 Vault가 매 생성/회전마다 그 자리에서 예측 불가능한 키를 만든다.

**비밀 보장**은 두 층위로 나뉜다.
1. **저장 계층**: Transit named key도 다른 모든 시크릿과 동일하게 keyring으로 직렬화된 뒤 [[01_아키텍쳐]]의 **Barrier(AES-256-GCM)**로 암호화되어 Storage Backend에 저장된다. Barrier를 여는 루트 키는 서버 시작 시 seal 상태이며, [[00_용어]]에서 정리한 **Shamir's Secret Sharing**(또는 Auto Unseal)으로 threshold 이상 조각이 모여야만 메모리에 평문으로 재구성된다 — Transit 키의 비밀성은 결국 이 barrier 루트 키의 비밀성에 종속된다.
2. **API 설계 계층**: Encrypt/Decrypt/Sign/HMAC 등 모든 연산은 Vault 프로세스 내부에서 키를 직접 다루고, 응답에는 연산 결과만 담길 뿐 키 자체는 절대 포함되지 않는다(HMAC 관련 이전 질문에서 `path_hmac.go` 소스로 이미 확인한 원리와 동일). 기본값이 `exportable=false`, `allow_plaintext_backup=false`(공식 API 문서)라서 원본 키를 꺼낼 방법 자체가 없고, 키 생성 시점에 명시적으로 `exportable=true`를 켜야만 `/transit/export/:key_type/:name`으로 꺼낼 수 있으며 그마저도 Vault Policy(ACL)로 통제된다. 이 옵션들은 한번 켜면 다시 끌 수 없는 one-way 설정이다.

즉 "자동 생성"은 CSPRNG(`crypto/rand`)가, "비밀 보장"은 (a) barrier 암호화 + unseal 절차라는 저장 계층 보호와 (b) API가 기본적으로 평문 키를 반환하지 않는 설계, 이 두 가지가 함께 담당한다.

## Q. https://developer.hashicorp.com/vault/docs/secrets/transit/key-wrapping-guide 이건 어떤내용에 대한 가이드임? (2026-08-27)

**A.**
Transit의 **BYOK(Bring Your Own Key) — 외부에서 생성한 키를 Vault로 안전하게 import하는 방법**을 다루는 가이드다. 이전 질문 답변에서 "BYOK도 공식 유스케이스로 제시된다"고만 짧게 언급했던 부분의 구체적 구현이다.

**래핑 방식(하이브리드 봉투 암호화)**:
1. 임시 256-bit AES 키를 생성해 **KWP(Key Wrap Protocol)**로 실제 가져올 키(target key)를 감싼다.
2. 그 임시 AES 키를 Vault가 제공하는 **4096-bit RSA wrapping key**로 **RSA-OAEP**(SHA-256 등) 암호화한다.
3. 래핑된 AES 키 + 래핑된 target 키를 이어붙여 base64 인코딩한다.

대칭키(AES-KWP)는 임의 길이 키를 빠르게 감쌀 수 있지만 안전한 전달 수단이 따로 필요하고, 비대칭키(RSA-OAEP)는 전달은 안전하나 큰 데이터 직접 암호화엔 비효율적이라 — 두 방식을 결합해 target 키가 평문으로 노출되는 구간을 없앤 구조다.

**절차**: `vault read transit/wrapping_key`로 Vault의 RSA 공개키 조회 → 클라이언트 측에서 target 키를 위 방식대로 이중 래핑 → `vault write transit/keys/<name>/import ciphertext=$CIPHERTEXT hash_function=SHA256 type=$KEY_TYPE`로 import. 소프트웨어 키(Go 라이브러리 예시)와 HSM 저장 키(AWS CloudHSM 예시) 두 시나리오를 모두 다룬다.

**관련 노트:** [`notes/03_시크릿엔진.md`](../notes/03_시크릿엔진.md#transit-키-importbyok--key-wrapping-guide)

## Q. transit 사용시 base64를 권장한다는데, 일반텍스트로 넣어도 큰 문제없는지. base64로 인코딩한 값을 저장한다는거 자체가 복잡해질거 같은데. (2026-08-27)

**A.**
"권장"이 아니라 **강제 요구사항**이다. base64가 아닌 값을 `plaintext`로 보내면 `{"errors":["failed to base64-decode plaintext"]}` 에러로 요청 자체가 거부된다(공식문서: `plaintext` 파라미터는 "base64 encoded plaintext"로 명시).

**강제하는 이유**: "Vault does not require that the plaintext is 'text'. It could be a binary file such as a PDF or image."(공식문서) — Transit은 문자열뿐 아니라 임의 바이너리(PDF, 이미지 등)도 암호화 대상으로 다룬다. 요청/응답이 JSON(텍스트 포맷)인데 임의 바이트를 그대로 넣으면 제어문자나 잘못된 UTF-8 시퀀스로 파싱이 깨질 수 있어, 데이터 종류와 무관하게 base64로 일괄 안전하게 감싸도록 강제하는 것이다.

**"저장이 복잡해질 것 같다"는 우려는 오해다** — base64는 API 호출 경계에서만 쓰이는 일시적 전송 인코딩이지, 영구 저장 형식으로 관리해야 하는 게 아니다.
- encrypt 호출 직전에 원본을 base64 인코딩해 보내는 것(1회성)
- 응답으로 받는 `ciphertext`(`vault:v1:...`)는 그 문자열 그대로 저장하면 됨 — 저장 시 추가 인코딩/디코딩 불필요
- decrypt 호출 직후 응답의 base64 `plaintext`를 1회 디코딩하면 원본 복원

즉 "encrypt 직전 1회 인코딩 / decrypt 직후 1회 디코딩"만 필요하고, 대부분의 Vault 클라이언트 SDK가 이를 자동 처리해준다.

**관련 노트:** [`notes/03_시크릿엔진.md`](../notes/03_시크릿엔진.md#base64는-권장이-아니라-필수--왜-강제하는가)

## Q. 예시에 보면, base64로 만들려면 클라이언트측에서 커맨드를 추가해야하는거 같은데? 그리고 공식문서 cli로만 나와있는데 http요청으로 사용시 엔드포인트에 post로 필드를 전달하기만 하면 되는지? 이에 대한 문서는 어떻게 정리되어있는지. (2026-08-27)

**A.**
둘 다 맞다.

**base64 인코딩은 Vault가 대신 해주지 않고 호출자(클라이언트) 책임이다.** CLI 예시의 `plaintext=$(base64 <<< "...")`처럼 `base64` 커맨드를 앞에 붙이는 이유가 이것이다. HTTP로 직접 호출할 때도 동일하게 요청 본문에 넣기 전에 각 언어 표준 라이브러리로 사전 인코딩해야 한다(Python `base64.b64encode()`, Node `Buffer.from(str).toString('base64')`, Go `base64.StdEncoding.EncodeToString()` 등).

**HTTP 요청 시에는 맞다 — 엔드포인트에 POST로 JSON body만 실어 보내면 된다.** 공식 HTTP API 문서(`/vault/api-docs/secret/transit#encrypt-data`)에 curl 예시가 별도로 나와 있다:
```bash
curl --header "X-Vault-Token: ..." --request POST --data @payload.json \
  http://127.0.0.1:8200/v1/transit/encrypt/my-key
```
body: `{ "plaintext": "dGhlIHF1aWNrIGJyb3duIGZveAo=" }` → 응답: `{ "data": { "ciphertext": "vault:v1:..." } }`. decrypt도 동일 패턴(`POST /v1/transit/decrypt/:name`).

**문서 구조**: `developer.hashicorp.com/vault/docs/secrets/transit`(개념/개요, CLI 예시 위주)와 `developer.hashicorp.com/vault/api-docs/secret/transit`(HTTP API 레퍼런스, 엔드포인트별 method/헤더/curl/JSON 스키마 명시)로 역할이 나뉘어 있다. HTTP로 직접 붙일 때는 후자가 1차 근거다. CLI는 결국 이 HTTP API를 감싸는 래퍼일 뿐, CLI/HTTP 모두 동일한 REST 엔드포인트를 호출한다.

**관련 노트:** [`notes/03_시크릿엔진.md`](../notes/03_시크릿엔진.md#cli-예시-vs-http-api-직접-호출--문서가-나뉘어-있는-구조)

## Q. 루아도 vault를 다룰수있는 sdk 있음? 없다면 decrypt한 다음에 base64가 오면 그대로 대조해야될거같은데 저장된 것은 key를 base64 형태로 바꾸고 encrypt한것일 테니까? (2026-08-27)

**A.**
**Lua 전용 SDK는 공식/커뮤니티 모두 없다.** 공식 클라이언트 라이브러리 목록(`/vault/api-docs/libraries`)에 HashiCorp 공식 Go/Ruby, 커뮤니티 C#/Java/Python/Node.js/Rust 등은 있지만 Lua는 없다. OpenResty/nginx-lua 생태계에도 전용 `lua-resty-vault` 라이브러리가 없어, 범용 HTTP 클라이언트(`lua-resty-http`)로 Vault REST API를 직접 호출하는 게 표준 패턴이다. 다만 Transit API 자체가 단순한 POST+JSON이라 SDK 부재가 구현 난이도를 크게 높이진 않는다.

**base64 대조 로직**: base64가 **두 개의 다른 레이어**일 수 있다는 점을 구분해야 정확하다.
- **레이어 A(필수, API 전송용)**: `encrypt` 요청/`decrypt` 응답의 `plaintext` 필드에 강제되는 base64 — 저장 내용이 아니라 API 왕복 시에만 존재하는 포장지다. Vault는 요청 시 이를 디코딩해 원본 바이트를 암호화한다.
- **레이어 B(선택, 애플리케이션 설계)**: "키 자체를 base64로 바꾼 뒤" 그걸 암호화 대상으로 삼는 것 — Vault가 강제하는 게 아니라 애플리케이션이 결정하는 부분이다.

질문하신 "저장된 것은 key를 base64로 바꾸고 encrypt한 것"이라는 전제(레이어 B 사용)가 맞다면, decrypt 응답에서 **레이어 A만 1회 디코딩**하면 남는 값이 바로 그 base64 key 문자열(레이어 B) 자체이므로 **그대로 대조하는 게 맞다** — 추가 디코딩 불필요. 다만 key가 원래 읽을 수 있는 문자열이라면 레이어 B를 추가할 이유가 없다: 원본 문자열을 그대로 encrypt에 넘기고 decrypt 후 1회 디코딩하면 원본 그대로 돌아온다 — 이쪽이 더 단순하다. 레이어 B는 key가 임의 바이너리일 때만 의미가 있다.

**더 근본적인 제안**: 어차피 SDK 없이 `lua-resty-http`로 직접 POST해야 하는 상황이면, `encrypt`/`decrypt`보다 **HMAC + `verify`**가 낫다. `verify`는 비교를 Vault 내부에서 상수시간으로 처리해 `{valid: true/false}`만 반환하므로 key 평문이 Lua로 왕복할 필요가 없고 base64 이중 레이어 문제 자체가 사라진다. 구현 난이도는 동일(둘 다 POST+JSON)하므로 굳이 평문 왕복 경로를 택할 이유가 없다.

**관련 노트:** [`notes/03_시크릿엔진.md`](../notes/03_시크릿엔진.md#lua에는-전용-sdk가-없다--base64-레이어를-구분해서-이해해야-하는-이유)
**참고 링크:**
- https://developer.hashicorp.com/vault/api-docs/libraries

## Q. 암호화 할때 base64인코딩해서 보내고, 그 결과를 다시 decrypt하면 받는 것은 base64가 아닌 원래 문자열이 리턴됨? (2026-08-27)

**A.**
아니다. **decrypt 응답도 base64로 감싸진 채 그대로 돌아온다** — Vault가 원본 문자열로 자동 변환해서 주지 않는다. 공식 API 문서 응답 예시: `{"data":{"plaintext":"dGhlIHF1aWNrIGJyb3duIGZveAo="}}` — 이 값 자체가 원본을 base64 인코딩한 형태다.

이유는 지난 질문에서 정리한 "레이어 A(API 전송용 필수 인코딩)"가 요청뿐 아니라 **응답에도 대칭적으로 적용**되기 때문이다. Vault는 plaintext를 문자열/바이너리 구분 없이 일괄 base64로 주고받으므로, 원본으로 되돌리려면 **호출자가 decrypt 응답의 `plaintext`를 한 번 더 base64 디코딩**해야 한다.

흐름: 원본 문자열 → base64 인코딩(레이어 A) → encrypt 요청 → ciphertext 저장 → decrypt 요청 → base64로 감싸진 plaintext 응답(레이어 A) → 호출자가 직접 디코딩 → 원본 문자열.

**관련 노트:** [`notes/03_시크릿엔진.md`](../notes/03_시크릿엔진.md#encryptdecrypt-api-상세)

- https://developer.hashicorp.com/vault/api-docs/secret/transit#decrypt-data

## Q. https://developer.hashicorp.com/vault/docs/concepts/transform 의 tokenize sensitive data는 평문이랑 매핑되는 토큰으로 보관하란거임? (2026-08-27)

**A.**
맞다. 공식문서: "To support token decoding, Vault secures a cryptographic mapping of tokens and plaintext values in internal storage." — Tokenization은 민감 데이터를 무작위 생성 토큰으로 치환하고, 나중에 그 토큰을 다시 원본으로 되돌릴 수 있도록(decode) **토큰↔평문 매핑을 Vault 내부 storage에 암호화해서 보관**한다.

**Transit과 정반대 구조**: Transit은 "Vault doesn't store the data sent to the secrets engine"가 핵심 설계였는데, Tokenization은 반대로 **데이터(매핑) 저장이 기능의 전제조건**이다. 나중에 토큰만으로 원본을 복원해야 하니 매핑을 어딘가엔 보관해야 하기 때문이다.

**Transform 엔진의 세 방식 비교**:
| 방식 | 상태 저장 | 원본 복원 |
|---|---|---|
| Tokenization | Vault 내부에 토큰↔평문 매핑 저장 | 가능(decode) |
| FPE(형식 유지 암호화) | Stateless(결정론적 알고리즘) | 가능(decrypt) |
| Masking | — | 불가능(단방향) |

**주의**: Transform 엔진 자체가 **Vault Enterprise 전용**이다(공식문서: "requires a Vault Enterprise license with Advanced Data Protection (ADP)"). 지금까지 이 문서에서 다룬 KV/Database/PKI/Transit은 모두 OSS 기능이었는데 Transform은 처음 등장하는 Enterprise 전용 엔진이다.

**관련 노트:** [`notes/03_시크릿엔진.md`](../notes/03_시크릿엔진.md#transform--tokenizationfpemasking-enterprise-전용)
**참고 링크:**
- https://developer.hashicorp.com/vault/docs/concepts/transform

## Q. aes를 통해 암호화하는 것을 주고, 받는 것에 비해 장점이 뭐임? 토큰 전체탐색같은건 똑같이 지원이 안될거같은데. (2026-08-27)

**A.**
좋은 지적이다 — "동일 값 조회(전체탐색) 가능 여부"는 실제로 두 방식을 가르는 차이가 아니다. Transit도 `convergent_encryption` 옵션을 켜면 동일 평문이 항상 동일 ciphertext로 나오도록 만들 수 있어서, 그 부분만 놓고 보면 AES(Transit)와 Tokenization은 동률이다. 진짜 장점은 다른 지점에 있다.

1. **키 하나만 털려도 복원 가능한가 — 핵심 차이**: 공식문서(Tokenization Transform): "even stealing the underlying transform key does not allow [attackers] to recover the plaintext without also possessing the encoded token" — 토큰화는 키만으로는 원본 복원이 불가능하고 토큰↔평문 매핑 저장소까지 함께 확보해야 한다. 반면 AES 암호화는 ciphertext+key만 있으면 즉시 복호화된다. ciphertext는 보통 데이터와 함께 유통되므로, 키 하나가 뚫리면 그 키로 암호화된 모든 ciphertext가 즉시 위험해진다. Tokenization은 "키 탈취"와 "매핑 DB 탈취"라는 서로 다른 두 자원을 동시에 확보해야 하는 구조라 방어선이 하나 더 있다.
2. **규제/컴플라이언스 범위 축소**: HashiCorp 공식 블로그: "Tokens being considered replacements exonerates them from a number of compliance regulations, because they do not possess any inherent relationship to the original plaintext." — PCI-DSS 등은 암호화된 데이터도 여전히 민감 데이터로 취급하는 경우가 많은데, 토큰은 원본과 수학적 관계가 없다고 간주되어 규제 범위 자체가 줄어드는 실무적 이점이 있다.
3. **포맷 유지(스키마 호환성)**: Transit ciphertext는 가변 길이 base64 문자열이라 기존 DB 컬럼(예: 16자리 카드번호)에 넣으려면 스키마 변경이 필요한 경우가 많다. Tokenization/FPE는 원본과 동일한 길이/형식 유지가 가능해 레거시 스키마를 안 건드려도 된다.

다만 HashiCorp도 "vaultless tokenization"보다는 FPE/Transit이 더 나은 보안 속성을 갖는다고 언급하므로, Tokenization이 무조건 우월한 건 아니고 레거시 스키마 제약·컴플라이언스 요구 등 상황에 따른 트레이드오프다.

## Q. 이 정도로 많은 요청이 있다면(06 문서의 Adobe 월 8억 건, athenahealth 하루 3억 건 등), 환경변수만 저장한 게 아니라 secret KV엔진에서 자주 불리는 어떤 것을 저장한 것 같은데, 이건 비권장되는 방식 아님? 예를 들어 /{consumer_name} secret 엔드포인트에서 자주 불리는 비밀들을 관리했을 것 같은데. (2026-08-27)

**A.**
방향은 맞다. 공식 문서가 정확히 이 시나리오를 경고한다.

Vault Agent Caching 튜토리얼의 "Challenge and solution" 절: "Depending on the location of your Vault clients and its secret access frequency, you may face some scaling or latency challenge. Even with Vault Performance Replication enabled, **the pressure on the storage increases as the number of token or lease generation requests increase**." — 애플리케이션이 매 비즈니스 요청마다 살아있는 Vault 호출로 시크릿을 가져오면, 요청량이 커질수록 그 부하가 그대로 Vault Storage Backend에 전이된다는 것을 공식 문서가 명시하고 있다.

다만 **정확히 무엇이 비권장인지는 구분해야 한다**: `/{consumer_name}` 같은 소비자별 경로로 KV를 나눠 저장하는 것 자체(경로 설계)는 전혀 문제가 아니다. 공식 문서가 지목하는 건 "그 경로를 요청 처리 흐름 안에서 매번 살아있게(synchronously) 호출하는 것"이다. 권장 대안은 **캐싱**:
- 토큰/동적 리스는 **Vault Agent** caching이 담당.
- **정적 KV v1/v2** 전용 캐싱은 **Vault Proxy**의 static secret caching인데, 이건 Enterprise의 이벤트 알림 시스템에 의존해서 **Vault Enterprise 전용**이다("Vault Proxy utilizes the Enterprise only Vault event notification system feature for cache freshness. As a result, static secret caching can only be used with Vault Enterprise installations." — 공식문서). OSS라면 이 공식 기능을 못 쓰니 애플리케이션이 직접 캐싱을 구현해야 한다.

**한계**: [[06_실제사용사례]]에서 다룬 Adobe·athenahealth의 공식 발표는 요청량 수치만 줄 뿐, "매 요청마다 직접 호출했다"거나 "캐싱을 안 썼다"고 확인해주진 않는다("확실하지 않음"). 다수 애플리케이션 인스턴스가 각자 주기적으로(lease 갱신 등) 조회하는 구조만으로도 그 정도 총량이 나올 수 있어, 실제로 어느 쪽이었는지는 공식 자료만으로 단정할 수 없다. 다만 공식 문서가 정확히 이 규모의 문제를 풀기 위해 캐싱 기능을 만들었다는 점은 확인된다.

## Q. Vault Proxy는 어디에 있는 구조임? vault server 앞단에 있는 구조임? Enterprise 라면? (2026-08-27)

**A.**
정반대다 — **서버 앞단이 아니라 클라이언트(애플리케이션) 옆**에 있다.

- 공식문서: "Vault Proxy is a **client daemon**", 설치 가이드는 "Download the Vault binary **where the client application runs** (virtual machine, Kubernetes pod, etc.)"라고 명시한다. 즉 로드밸런서/게이트웨이처럼 서버 앞단에 두는 게 아니라, **애플리케이션이 실행되는 위치**에 함께 배포하는 로컬 데몬이다.
- 배치 단위는 **클라이언트 1개당 1개**(사이드카)가 원칙이다. Kubernetes에서는 애플리케이션과 같은 Pod의 사이드카 컨테이너로 주입되는 게 표준 패턴이고, 공식 가이드는 Pod 밖에 별도로 둬서 여러 클라이언트가 공유하는 구성을 명시적으로 경고한다 — "It's also possible to deploy the proxy outside of the pod but doing that will use the **same token for all of the client requests**, which is a big security risk."
- 요청 흐름: 애플리케이션 → (로컬) Vault Agent/Proxy → Vault 서버. Agent/Proxy가 auto-auth로 대신 인증하고 응답을 캐싱해뒀다가, 캐시 미스이거나 만료됐을 때만 실제로 서버에 요청을 전달한다.

**Enterprise라면?** — **위치는 안 바뀐다.** OSS든 Enterprise든 Agent/Proxy는 항상 클라이언트 옆에서 실행되는 동일한 구조다. Enterprise가 바꾸는 건 위치가 아니라 **Proxy가 의존하는 서버 쪽 기능**이다:
- 정적 KV 캐싱은 캐시 신선도 확인을 위해 **Vault event notification system**을 쓰는데, 이 이벤트 시스템 자체가 **Vault 서버의 Enterprise 전용 기능**이다.
- 방식은 폴링이 아니라 **구독(subscribe)형**이다 — Proxy가 `sys/events/subscribe/kv*` 구독 권한이 있는 auto-auth 토큰으로 서버의 KV 이벤트 피드를 구독해두고, 캐시된 시크릿과 관련된 변경 이벤트가 오면 캐시를 무효화/갱신한다.
- 그래서 "Proxy가 Enterprise 전용 소프트웨어"가 아니라 "정적 KV 캐싱이라는 특정 기능이 의존하는 서버 쪽 기능이 Enterprise 전용"인 것이다 — Proxy 자체(auto-auth, 토큰/리스 캐싱, API 프록시)는 OSS 서버에서도 정상 동작한다.

## Q. Vault에서 결국 핵심이 되는 기능은 동적 비밀 발행이고, 정적 비밀로는 환경변수에 관한 것을 쓰는 것 같은데. 정적 비밀에 조회되는 것을 사용할 경우 Proxy 혹은 로컬 캐싱을 사용하는 게 베스트 프랙티스에 가까울까? (2026-08-28)

**A.**
"매 요청마다 Vault를 직접 호출하지 말고 캐싱을 거쳐라"는 방향은 공식문서가 명시적으로 권장하는 게 맞다. 다만 "환경변수 주입"과 "캐싱"은 사실 **서로 다른 축의 문제**라서, 질문을 그대로 이분법(Proxy vs 로컬 캐싱)으로 좁히면 놓치는 선택지가 있다.

- **축 1: 앱이 Vault를 알아야 하는가.** Vault Agent의 Template 기능(`env_template`/`exec` 블록, Process Supervisor 모드)은 정적 시크릿을 환경변수로 렌더링해 애플리케이션 프로세스에 주입한다. 공식 튜토리얼("Export secrets as environment variables with Vault Agent")은 전통적 방식(배포 스크립트가 최초 1회만 env var를 세팅)의 한계를 "시크릿이 바뀌면 수동으로 갱신해야 한다"고 지적하고, Agent 방식의 목적을 이렇게 설명한다 — "This application does not need to know about Vault." / "Vault Agent can handle the authentication and secrets retrieval so that your application can remain Vault unaware." 즉 이건 **부하 절감이 1차 목적이 아니라 "앱 코드에서 Vault 의존성 제거"가 목적**이다. `staticSecretRenderInterval`로 주기적 재렌더링, `restart_on_secret_changes`로 값 변경 시 프로세스 재시작이 가능하다.
- **축 2: Vault 서버 호출 빈도를 줄이는가.** 앱이 API 형태로 매 요청마다 Vault를 호출하는 구조라면 이게 진짜 "캐싱"이 필요한 지점이다. Vault Agent Caching 튜토리얼의 "Challenge and solution" 절이 이 문제를 직접 지목한다 — "Depending on the location of your Vault clients and its secret access frequency, you may face some scaling or latency challenge... the pressure on the storage increases as the number of token or lease generation requests increase." 정적 KV 전용 캐싱은 **Vault Proxy**가 담당하지만, 이벤트 구독 기반 신선도 갱신에 의존해 **Vault Enterprise 전용**이다("static secret caching can only be used with Vault Enterprise installations." — 공식문서).
- 두 축은 실무에서 겹친다 — env_template 방식도 결과적으로 Agent가 로컬에 시크릿을 쥐고 있다가 필요할 때만 재조회하므로 서버 호출 빈도를 줄이는 효과를 겸한다. 다만 이건 폴링(주기적 재조회)이지, Enterprise Proxy의 이벤트 기반 즉시 무효화와는 신선도 보장 수준이 다르다.

정리하면:

| 상황 | 권장 패턴 |
|---|---|
| 앱을 Vault로부터 완전히 분리하고 싶고, 재배포/재시작 주기로 반영돼도 충분 | Vault Agent Template → 환경변수/파일 렌더링 |
| 앱이 API 호출 형태를 유지하며 다수 인스턴스 요청을 줄이고 싶고 Enterprise 보유 | Vault Proxy의 static secret caching |
| OSS이고 앱이 런타임 중 API 호출을 유지해야 함 | 공식 캐싱 기능 없음 — 앱 자체 in-memory 캐시/폴링을 직접 구현해야 한다(공식문서가 구체 레시피를 제공하지 않아 "확실하지 않음") |

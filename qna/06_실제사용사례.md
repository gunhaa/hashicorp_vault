# 대기업 Vault 실제 사용사례 Q&A

`notes/06_실제사용사례.md`와 짝을 이루는 질문/답변 기록입니다. 이 주제로 질문이 들어올 때마다 아래에 항목을 추가합니다.

## Q. 실제 사용사례에서 핵심은 "어떻게 사용되었는가"다 — 어떤 비밀을, 어떤 API로, 어떻게 보관했는지. 트래픽이 많았다면 왜 많았는지도 (2026-08-27)

**A.**
기존 문서가 복제 토폴로지·규모 수치 위주였고 "무엇을 어떤 엔진으로 저장/조회했는가"와 "왜 트래픽이 많았는가"는 각 사례에 한 줄 정도로만 다뤄져 있었다. 이 지적에 맞춰 세 사례의 1차 공식 자료(HashiCorp case study 페이지, HashiConf/webinar 발표 콘텐츠)를 다시 조사했다.

**조사 결과, 세 사례의 공개 수준이 서로 다르다:**

- **Adobe**: 시크릿 종류는 구체적으로 공개되지 않음("확실하지 않음"). 확인되는 건 KV v2 엔진 + cost center 태깅, 그리고 한 팀이 실수로 1,000만 건 이상의 key-value를 넣은 사고. 트래픽 관련해서는 "왜 원래 많은가"의 직접 설명은 없지만, 관련 사고가 하나 확인됨 — 내부 사용자가 한 번에 60~70만 개 service token을 요청해 리소스를 소진시켰고, service token이 클러스터 간 복제되는 부하 문제와 맞물려 batch token 도입 계기가 됨.
- **Starbucks**: "정적 KV~단기 PKI 인증서~동적 DB/클라우드 자격증명까지" 넓은 범위를 지원한다는 일반론과, 디바이스 종류가 POS 단말기부터 온도 센서까지 다양하다는 언급만 있고 디바이스별 구체적 시크릿 매핑은 비공개. 엔진은 PKI 사용만 명확(1년 인증서 → 짧은 TTL 전환). 전달은 response wrapping + Vault Agent caching. 트래픽 수치 자체가 공개되지 않아 이유도 추정하지 않았다.
- **athenahealth**: 세 곳 중 가장 구체적 — 별도 웨비나(HashiCorp Justin Weissig + athenahealth SRE 리드 Jeff Byrnes)에서 시크릿 종류를 "service account, application secret, key, TLS 인증서, 비상 접근 계정, SSH 키, DB 자격증명"으로 명시. 접근 방식은 Vault Agent 사이드카와 앱이 Vault API에 직접 붙는 방식(Consul 서비스 디스커버리로 엔드포인트 탐색)이 병행. 다만 PKI 엔진은 웨비나 시점에 "로드맵"이라고 밝혀, 당시엔 주로 정적(static) 시크릿 위주였을 가능성이 있음(추정). **수치 불일치도 발견**: 웨비나는 "하루 9천만 건", 이후 공식 case study는 "하루 3억 건"으로 서로 다르다 — 시점 차이로 보이며 두 자료 모두 원인 설명은 없다.

**반영**: 각 회사 절에 `#### 무엇을, 어떤 API로 저장/전달했는가`, `#### 요청량이 높았던 이유` 소단락을 추가하고, 비교 표에 "저장 시크릿", "시크릿 엔진", "접근 방식", "요청량이 높은 이유" 행을 추가했다. 공식 자료에 없는 부분은 "확실하지 않음"/"비공개"로 명시하고, 정황상 추정만 가능한 부분은 "추정"이라고 못박아 단정하지 않았다.

## Q. password/카드번호 같은 민감 정보를 암호화 상태로 서버에 저장할 때 사용하는 예시가 없는 것 같은데, 이에 관한 사례 추가 가능함? 현재 사례 추가 설명으로 가능하다면 해당 내용 추가 (2026-08-27)

**A.**
먼저 기존 세 사례(Adobe/Starbucks/athenahealth)의 공식 자료에 이 패턴(카드번호·비밀번호를 암호화해서 자체 DB에 저장 — Vault **Transit/Transform** "encryption as a service")이 실제로 언급되는지부터 확인했다. 세 곳 모두 시크릿 스토리지·동적 자격증명·PKI 중심이었고, 이 패턴은 없었다("확실하지 않음" 수준도 아니고 아예 미언급). 그래서 "기존 사례에 추가 설명으로 끼워 넣는" 방식은 정직하지 않다고 판단해, 대신 이 패턴을 실제로 다루는 **네 번째 공식 사례**를 새로 찾아 추가했다.

**찾은 사례**: GitLab 엔지니어 Nicholas Klick과 DataRobot 엔지니어 Apollo Catlin이 발표한, 두 사람이 과거 함께 근무했던 결제 회사(연 수십억 달러 규모 결제 파이프라인, **2천만+ 신용카드 레코드**)의 PCI 컴플라이언스 아키텍처 사례. 다만 이 발표 자체도 SSH 인증서/동적 DB 자격증명/PKI 로테이션/RBAC/감사 로깅 위주였고, **카드번호를 실제로 어떤 엔진·API로 암호화해 저장했는지는 상세히 다루지 않았다**("encryption as a service"라는 표현만 등장).

**그래서 두 자료를 명확히 구분해서 추가함**:
1. 실제 발표에서 확인되는 내용(회사 규모, Vault 활용 영역) — "이 사례" 절.
2. 그 발표가 다루지 않은 "카드번호를 구체적으로 어떻게 암호화·저장하는가"는, HashiCorp 공식 블로그("Achieving PCI compliance...")와 공식 문서(Transform secrets engine)가 제시하는 **권장 패턴**으로 보충 — "(보충) 공식 권장 패턴" 절에 인용, 이 회사의 실제 구현이 아니라 공식문서 기준 일반 패턴임을 명시.

**핵심 기술 내용**: Transform 엔진(Vault **Enterprise**/HCP Vault Dedicated 전용, OSS엔 없음)은 **FPE**(Format-Preserving Encryption, 가역적, 원본과 같은 포맷 유지 — `transform/encode`↔`transform/decode`)와 **Tokenization**(비가역, 원본과 무관한 토큰으로 치환, stateful) 두 방식을 지원한다. 애플리케이션은 원본 값을 절대 저장하지 않고 `transform/encode`가 반환한 값만 DB에 저장하며, 원본이 필요할 때만 `transform/decode`로 역변환을 요청한다. PCI-DSS 관점에서는 tokenization을 쓰면 토큰만 다루는 시스템이 카드 데이터 컴플라이언스 감사 범위에서 빠질 수 있다는 게 핵심 이점 — HashiCorp 공식 블로그가 이를 PCI-DSS Requirement 2/3/4(특히 저장 데이터 보호를 다루는 Req 3)에 매핑한다. Tokenization의 키 로테이션은 `POST /transform/tokenization/keys/:transform_name/rotate` API로 수행한다.
